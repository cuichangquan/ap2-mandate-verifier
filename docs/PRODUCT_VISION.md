## 現在のプロジェクト目標と優先順位（Owner決定・2026-10-28 JST）

**AP2が普及したとき、Ruby開発者が最初に選ぶOSSになること。**

安全な検証品質を維持しながら、これからは「開発者が実際に試し、導入し、広められること」を優先する。Google等からの公式認定や実Issuerの登場を、OSSの利用体験改善の開始条件にはしない。

1. **使ってみたくなるデモを完成・公開する。** ブラウザ上で正常・改ざん・期限切れの検証結果と拒否理由を比較できるようにする。現時点で[ローカルRailsデモ](https://github.com/cuichangquan/ap2-mandate-verifier-demo)は存在し、一般利用者がURLだけで体験できる公開サイトはこれからの対象。
2. **Rails開発者が短時間で試せる導線を整える。** 公開済みGemの実APIに一致するQuick Start、最小実行例、入力・信頼前提、よくある失敗を分かりやすく示す。未実装機能を使用可能と案内しない。
3. **利用者と認知度を増やす。** GitHub README、技術記事、デモへの導線、問い合わせ・フィードバックを改善する。成果は単なる研究PR数ではなく、体験・導入・利用者の増加で判断する。

公開デモでは保存済みの**合成入力だけ**を扱い、実Issuer・実決済・任意の秘密鍵やMandate入力を受け付けない設計を起点とする。公開URL・サーバー運用・アクセス制限・資源制限等は別途レビュー・承認する。ここに記した優先順位は、公開デプロイや追加実行の承認ではない。

## Ruby開発者に届けたい価値

**Ruby開発者が、AP2の複雑な署名・委任ルールを自作せず、安全に扱えるGemを目指します。**
安全性を主張だけで成立させず、対応仕様・信頼の前提・独立した検証証拠・未対応事項を利用者が確認できる形で提供します。
固定profileは初期の足場であり、最終目的ではありません。最初は検証専用Gemでよく、そのコアを堅実に完成させてから、最終的にAP2 Ruby SDKへ広げる方向を目指します。

## 大切にする設計方針

1. **AP2規格に忠実で、対応範囲が明確。** 対象の仕様版・profile・署名形式・委任形状・制約を明示します。規格由来の要件とGem独自の厳格化を区別し、対応範囲を証拠とともに段階的に広げます。未対応の正規AP2データを、規格違反と決めつけません。
2. **安全な検証コア。** 署名、委任と鍵の結合、署名対象原文と開示の完全性、購入内容binding、期限、Schemaと対応制約を検査します。署名だけ・可視部分だけの成立を成功へ昇格せず、不明・未知・未対応を推測で許可しません。
3. **Rubyから理解して使える。** 明確なAPIと入力契約、失敗理由とエラー対応、導入例・使用例、対応Ruby/依存/provider、版更新時の互換性方針を整えます。架空のAPIを実装済みとして案内せず、検証失敗と処理系障害を区別します。
4. **Rails非依存のコア。** Ruby単体で利用できる検証コアを保ちます。必要なら将来、Rails向けの別Gemでアプリ連携を補助する余地を残します。別Gemの作成や構成は未決定です。

## GemとHostの責任分担

理想は、**「AP2の共通処理はGem、サービス固有の判断と実行はHost」**です。
目指すのは「決済システム全部入り」ではなく、AP2を正しく扱うRuby SDKです。

### どの処理を誰が担当するか

発行・提示生成・Payment Mandate対応は、以下では**将来の役割案**です。現在のGemに実装済みという意味ではありません。

| 処理 | Gem / 将来SDKが支援すること | Host・外部サービスが担当すること |
| --- | --- | --- |
| 検証 | 現在の中心機能。対応範囲の署名・委任・購入内容・期限・制約を検査しEvidenceを返す | 信頼元と最新状態を供給し、検証後の最終業務判断を行う |
| 発行（将来） | AP2形式の組み立て、署名対象の構成・署名処理等の共通手順を支援 | 誰に何を許可するか、どの鍵で署名するかを決定。秘密鍵の保管・利用権限・鍵管理はHost側。具体的な署名連携APIは未決定 |
| 提示生成（将来） | 必要な情報・証明をAP2形式に組み立てる処理を支援 | 提示する情報と目的・相手方への開示を判断し、必要な正本・鍵利用手段を管理 |
| Host運用 | 現在は検証入口と結果を提供。将来の連携補助も責務境界を保つ | 注文DB、nonce原子消費・二重処理防止、監視、Issuer選定、最新失効・信頼時計・状態を管理 |
| 決済 | 将来、Payment Mandateの生成・検証などAP2の証明部分を支援する方向を検討 | Hostが支払いの可否・実行要求・冪等性を判断し、決済サービスが実際の支払いを処理 |

Gemが署名処理を支援しても、用途の許可や秘密鍵管理を引き受けたり、決済を自動許可したりするわけではありません。まず検証コアを固め、次に発行・提示等へ広げる順序です。

### 現行の検証コアとHostの境界

| Gemの責任 | 利用側Hostの責任 |
| --- | --- |
| 既存の厳格入力上限、登録/選択/profileの整合、署名・委任・原文/開示閉包、Schema/制約、購入/Host binding、供給時刻での期限交差を検査 | 信頼する発行主体・用途・鍵の真正な出所を決定し、最新の失効・登録状態、信頼時計、現在注文/challengeを供給 |
| 対応範囲の検査事実をEvidenceとして返し、不正入力や判断不能を成功にしない | Evidenceの使用直前にも最新状態を照合し、nonceの原子消費と注文CAS、結果不明時の照会/再試行境界、最終業務判断・決済を担当 |

**EvidenceはALLOWでも購入許可でも決済完了でもありません。** Gemは外部の信頼元や失効情報の最新性を独立証明しません。任意の公開鍵の登録だけでは信頼は成立せず、Hostが信頼根拠や最新状態を確認できなければHOLDです。
Gem自身が実装済みの検査をHostへ移して省略する方針ではありません。現行Evidenceは信頼する同一Rubyプロセス内の不変な検査事実であり、JSON化したHashから真正性を復元するAPIではありません。
