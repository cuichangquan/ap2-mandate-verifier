## 現在のプロジェクト目標と優先順位（2026-10-28の目標／2026-11-01の1.0.0準備方針）

**AP2が普及したとき、Ruby開発者が最初に選ぶOSSになること。**

安全な検証品質を維持しながら、「開発者が実際に試し、導入し、広められること」を優先する。目標はGoogle等からの公式認定を得ることではなく、Ruby開発者に選ばれるOSSになること。公式認定や実Issuerの登場を、OSSの利用体験改善の開始条件にはしない。

1. **フレームワーク非依存のAP2 Ruby SDKとして公開契約を固める。** 公開済み`0.8.0`のDirect／条件付き購入委任について、発行・提示・検証・Checkout Receipt確認を利用できる状態を土台とします。次の`1.0.0`では、公開API、対応profile、互換性、エラー、利用側の責任、保守範囲を明示し、実装と文書・配布候補が一致することを確認します。
2. **Ruby開発者が短時間で導入できる導線を整える。** Ruby単体で動くQuick Startと、Provider・Agent・Merchantの役割が分かる最小実行例を主な入口にします。入力・信頼前提、失敗と未確定結果の扱いも示します。[既存のRailsデモ](https://github.com/cuichangquan/ap2-mandate-verifier-demo)はSDKの利用例として活用します。Rails連携は本Gemの前提や1.0.0の完成条件にはしません。
3. **利用者と認知度を増やす。** GitHub README、技術記事、デモへの導線、問い合わせ・フィードバックを改善する。成果は単なる研究PR数ではなく、体験・導入・利用者の増加で判断する。

既存の導入文書と合成入力によるローカル実行例を改善し、具体的な不足がない研究・文書・PRを増やさない。デモは保存済みの**合成入力だけ**を扱い、実Issuer・実決済・任意の秘密鍵やMandate入力を受け付けない。Webサイト公開やサーバー運用は今回の対象外。ここに記した優先順位は、公開デプロイ・追加実行や既存の安全性HOLDの解除を承認しない。

## Ruby開発者に届けたい価値

**Ruby開発者が、AP2の複雑な署名・委任ルールを自作せず、安全に扱えるGemを目指します。**
安全性を主張だけで成立させず、対応仕様・信頼の前提・独立した検証証拠・未対応事項を利用者が確認できる形で提供します。
検証コアから始め、0.8.0では対応profileの発行・提示・検証・Receiptまでを備えたRuby SDKへ広がりました。1.0.0はこの公開契約を安定させる節目です。今後のprofile拡張は用途と検証根拠に応じて判断し、一般AP2の全機能対応を1.0.0の意味にはしません。

## 大切にする設計方針

1. **AP2規格に忠実で、対応範囲が明確。** 対象の仕様版・profile・署名形式・委任形状・制約を明示します。規格由来の要件とGem独自の厳格化を区別し、対応範囲を証拠とともに段階的に広げます。未対応の正規AP2データを、規格違反と決めつけません。
2. **安全な検証コア。** 署名、委任と鍵の結合、署名対象原文と開示の完全性、購入内容binding、期限、Schemaと対応制約を検査します。署名だけ・可視部分だけの成立を成功へ昇格せず、不明・未知・未対応を推測で許可しません。
3. **Rubyから理解して使える。** 明確なAPIと入力契約、失敗理由とエラー対応、導入例・使用例、対応Ruby/依存/provider、版更新時の互換性方針を整えます。架空のAPIを実装済みとして案内せず、検証失敗と処理系障害を区別します。
4. **フレームワーク非依存のRuby SDK。** 発行・提示・検証・Receipt確認をRuby単体で利用できる設計を保ちます。Webフレームワーク、ORM、注文DBを必須にせず、Railsアプリからも同じ公開APIを利用します。

## GemとHostの責任分担

理想は、**「AP2の共通処理はGem、サービス固有の判断と実行はHost」**です。
目指すのは「決済システム全部入り」ではなく、AP2を正しく扱うRuby SDKです。

### どの処理を誰が担当するか

発行・提示・検証・Receipt確認は、以下の対応profileに限って0.8.0で利用できます。Payment Mandateは将来の検討範囲です。

| 処理 | 現在のGemが支援すること | Host・外部サービスが担当すること |
| --- | --- | --- |
| 検証 | 対応範囲の署名・委任・購入内容・期限・制約を検査し、各APIの検査結果を返す | 信頼元と最新状態を供給し、検証後の最終業務判断を行う |
| 発行 | Merchant Checkout署名、ProviderによるDirect Closed／条件付きOpen、Agentによる条件付きClosedの組み立て・署名を支援 | 本人認証・同意・購入権限、許可条件、使用する署名者を決定。秘密鍵の保管・利用権限・鍵管理、外部署名サービスの可用性を管理 |
| 提示 | 対応形状の構造と原文bindingを確認し、署名済み原文を保持した提示を組み立て・復元する。提示処理だけでは署名の真正性を証明しない | 目的・相手方への開示を判断し、必要な署名済み原文を保持。Merchantで独立した信頼・現在状態による完全検証を行う |
| Receipt | アプリケーションが指定したSuccess／Errorの署名と、署名者・時刻・元のClosed SD-JWT参照の確認を支援 | 実際の業務結果を決定・保存。ErrorやReceipt未着を自動再購入の許可とせず、未確定状態を照会・調整 |
| Host運用 | 入力準備・復元、検証入口と結果を提供 | 注文DB、nonce原子消費・二重処理防止、監視、Issuer選定、最新失効・信頼時計・状態を管理 |
| 決済（将来の検討） | Payment Mandateの生成・検証などAP2の証明部分の支援を検討。現行SDKの対象外 | Hostが支払いの可否・実行要求・冪等性を判断し、決済サービスが実際の支払いを処理 |

Gemが署名処理を支援しても、用途の許可や秘密鍵管理を引き受けたり、決済を自動許可したりするわけではありません。Directと条件付き委任の契約は、それぞれ[Direct Checkout](BUYER_DIRECT_CHECKOUT.md)・[Conditional Checkout](CONDITIONAL_CHECKOUT.md)を参照してください。

### 現行の検証コアとHostの境界

| Gemの責任 | 利用側Hostの責任 |
| --- | --- |
| 既存の厳格入力上限、登録/選択/profileの整合、署名・委任・原文/開示閉包、Schema/制約、購入/Host binding、供給時刻での期限交差を検査 | 信頼する発行主体・用途・鍵の真正な出所を決定し、最新の失効・登録状態、信頼時計、現在注文/challengeを供給 |
| 対応範囲の検査事実をEvidenceとして返し、不正入力や判断不能を成功にしない | Evidenceの使用直前にも最新状態を照合し、nonceの原子消費と注文CAS、結果不明時の照会/再試行境界、最終業務判断・決済を担当 |

**EvidenceはALLOWでも購入許可でも決済完了でもありません。** Gemは外部の信頼元や失効情報の最新性を独立証明しません。任意の公開鍵の登録だけでは信頼は成立せず、Hostが信頼根拠や最新状態を確認できなければHOLDです。
Gem自身が実装済みの検査をHostへ移して省略する方針ではありません。現行Evidenceは信頼する同一Rubyプロセス内の不変な検査事実であり、JSON化したHashから真正性を復元するAPIではありません。
