**2026-10-13 JST / research-only / bounded candidate: LIMITED_DC05_OBSERVED / Phase 2-B HOLD.**

This is a follow-up to [DC04 bounded Ruby result](PHASE2A_DC04_BOUNDED_RUBY_FOLLOWUP.md), not a generic SD-JWT decoy feature. AP2 v0.2.0 source and official SDK are pinned to commit `b4587ac1d055888a73b4b21750973cffba961793`.

## Why a green SDK/schema result is not the security oracle

Selective-disclosure decoys appear as issuer-signed digest commitments even though there is no actual Disclosure the holder can reveal for them. The Root signature makes the digest authentic but does **not** tell the Merchant whether its hidden preimage is a decoy or an undisclosed authorization-bearing claim. The candidate's immutable fixed-Issuer policy therefore rejects unknown `_sd` regardless of what the official SDK's resolved Open and JSON Schema show.

The DC04 signed-decoy negative was a useful candidate regression, but did not explicitly report the exact **unresolved signed digest positions**, full schema for that variant or a separate DC05 acceptance gate. We do not count that earlier result as DC05.

## Independent signed experiment

- **O1/O2:** run the existing pinned official Python generator with ephemeral private signing keys, independently check the Issuer / Agent / Merchant JWSs, Terminal `sd_hash`, Host aud/nonce, Merchant Checkout JWT/hash. No secrets committed or uploaded.
- **O3:** separately scan the signed Root graph **starting at the JWT payload root** and following real Disclosure mappings, enumerating `_sd` and `...` commitments by exact path, SHA256 and presence. Require a **real unmatched object digest** generated by official `sd_jwt.create(add_decoy_claims=True)`. Record actual location, not an assumed root-only position; if no such digest is created, BLOCKED/HOLD.
- **O4:** independently record the actual official Open Schema for fully disclosed control and the decoy presentation. The official SDK may resolve both to the same Open and Schema VALID; neither implies disclosure completeness.
- **O5:** demand that the Ruby fixed-Issuer candidate accept **FULL first** as `LIMITED_POSITIVE`, then reject the authentically signed decoy with an explicit fixed-profile rejection rooted in its resolver. The rejection's `unsupported_profile` classification is derived from a bounded, observable Ruby code location and supported by O1–O3. Do not claim the Ruby code identified a decoy by examining its digest.
- **Replay:** save only the original synthetic signed Root / Disclosure / Terminal / Checkout JWT wires and trusted public keys; record run HEAD, official SHA, Python freeze, SHA256/byte-size manifest. The seven-day GitHub Actions artifact is content-addressed but **not permanent**.

Expected classification: `LIMITED_DC05_OBSERVED` if all independent oracles agree. Any invalid signature, no actual signed residual, wrong schema/control, or unrelated Ruby rejection => `RED_HOLD` / CI FAIL rather than a decoy security pass.

## Scope boundary

This is an intentionally restrictive issuer profile that can reject legitimate privacy-preserving AP2 presentations. It does not prove that a verifier can distinguish an actual decoy from a hidden authority claim from its digest alone, nor establish a supported generic decoy whitelist or full AP2/SD-JWT conformance. Root/Agent/Checkout evidence is **not** Host business ALLOW, buyer consent, nonce-CAS, revocation, receipt, HC06 or a payment.
